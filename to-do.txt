- Smart contract supports mint requests
- Smart contract supports transfer requests
- Smart contract supports burn requests
- Smart contract supports request approval and rejection
- Smart contract supports request cancellation
- Smart contract supports admin rotation
- Smart contract supports checker add/remove
- Local Anchor tests for mint, transfer, burn, admin rotation, checker management, and cancel flow are passing
- Backend integrates with the Anchor program on local validator
- Backend can bootstrap on-chain config and checker

- Admin portal supports:

  - execute on chain

Recommended Order

Stabilize the Solana integration boundary
Implement browser extension wallet integration
Refactor request execution for maker-side signing
Deploy and validate on devnet/testnet
Backfill legacy managed tokens
Add token detail/history UX
Do optional platform improvements last
Why this order
The browser-wallet work is your real priority, but doing it cleanly depends on first drawing a hard line between:

off-chain workflow and approvals
on-chain transaction preparation
client-side signing and submission
post-transaction recording
Your code already has a useful seam for this:

WalletConnectCard is a placeholder in the frontend
mark-ready already returns an executionPayload
backend execution is still centralized in executeReadyRequest
That means we do not need to redesign the whole app. We need to split the current backend-managed execution path into a reusable “prepare” path and a wallet-signed path.

Phase 1: Stabilize the Boundary
Goal: make the current backend flow and the future wallet flow coexist.

Work:

define which request types require browser signing first
keep MINT server-managed initially unless you want admin wallet signing in-browser too
formalize the payload shape for transfer/burn preparation
make Solana startup/bootstrap configurable so local dev doesn’t break the whole API
document localnet vs devnet/testnet env separation
Deliverable:

clear execution contract between frontend and backend
no accidental coupling between “approve request” and “submit on-chain tx”
Phase 2: Browser Extension Wallet Integration
Goal: connect Phantom or compatible wallets in the frontend.

Work:

add Solana wallet adapter dependencies and provider wiring
create app-level wallet context/provider
replace the disabled WalletConnectCard flow with real connect/disconnect/state UI
show connected address, cluster, and mismatch warnings
gate wallet-only actions behind connection checks
Deliverable:

frontend can connect a browser wallet reliably
wallet state is visible and reusable across pages
Phase 3: Maker-Side Signing Flow
Goal: move transfer/burn initiation away from backend-controlled maker keys.

Work:

add backend endpoints or service methods that prepare unsigned transactions or instruction payloads
let maker sign delegation / initiation steps in-browser
persist the resulting signature and any derived on-chain addresses
keep checker approval and executor steps compatible with the existing workflow
decide whether execution remains backend-submitted after approval or also becomes browser-submitted
Deliverable:

maker uses Phantom instead of server-side wallet assumptions for transfer/burn initiation
Phase 4: Devnet/Testnet Deployment
Goal: make the stack work off local validator.

Work:

finalize deployment target and env files
sync final program ID and IDL
deploy program
verify wallet flow, approval flow, and managed token flow on the target network
add a repeatable deployment checklist/script
Deliverable:

one verified non-local environment with known-good config
Phase 5: Backfill Managed Tokens
Goal: populate the registry with older mints created before persistence existed.

Work:

add a one-off script or admin-only sync path
scan known mint sources or on-chain history
upsert by mintAddress
preserve metadata like authorities and explorer links
log what was added vs skipped
Deliverable:

managed_tokens becomes complete, not just “newly created after feature launch”
Phase 6: Token Detail and History UX
Goal: make tokens first-class objects in the portal.

Work:

add token detail page from the managed tokens list
add copy/open-explorer actions
show related requests, balances, and transaction history
link wallets and token requests back to the token detail page
Deliverable:

better operational visibility without changing protocol logic
Phase 7: Optional Improvements
Only after the core flow is stable:

token metadata support
freeze/thaw admin actions
earlier request-to-on-chain-account linkage
deeper explorer links and account views
What I’d implement first
If you want me to start after this plan, I would begin with:

wallet adapter foundation in the frontend
backend prepare/sign boundary for transfer/burn
minimal end-to-end maker browser signing on localnet
That gives the highest-value missing feature first, without blocking later devnet deployment.
